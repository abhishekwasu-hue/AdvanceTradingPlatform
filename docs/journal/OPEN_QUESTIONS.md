# Journal module - open questions

Questions for the owner about the Journal module (`docs/specs/ATP_JOURNAL_MODULE_SPEC.md`, plan in
`docs/journal/PLAN.md`). Each has a provisional default so that the plan, and later the build, can go on. The same
rules as `docs/OPEN_QUESTIONS.md` apply: when a question is answered, mark it **answered**, note the answer, and change
the plan or the code if the answer differs from the default.

Nothing here is built before Z11 merges (owner decision OD-1).

| # | Question | Provisional default + reason | Applies to | Status |

Note: `app/tax/report.py` today uses the older method for options ("plus premium received on options sold"). J7-b aligns both reports on the same setting. A CA should confirm the default against the current ICAI guidance note before the report ships. Update: the Phase 0 tax report now has the setting (`TAX_FNO_TURNOVER_METHOD`, default `ABS_PNL`; `turnover_method` per request) and names the method it used; J7-b reuses it. | J7-b, `app/tax/report.py` | open |

| JM-11 | Mentor permissions. | Opt-in by the student, revocable at any time, with an expiry date (default none). | JM-12 | Verified P&L badge rules. | The badge shows only when: (a) every trade in the period came from broker API sync (fills with `source = BROKER_API`); (b) no fill or charge was edited by hand (grouping and notes edits are allowed); (c) sync covered every trading day of the period with no failed run; (d) broker vs computed P&L reconciled within tolerance on every day that has a broker statement. The card has no account number, client id or broker login. It shows the period, net P&L, number of trades and (optionally) return on the capital base, plus "the user's own account; past results; not investment advice". The link is signed and revocable, with a 30-day default expiry. Compliance note: ATP never uses user cards in its own marketing (SEBI rules on performance claims). | J7-c | open |
| JM-13 | Event calendar sources. | Seeded by an admin from official sources, each row with its source: the NSE expiry calendar (computed from `expiry_calendar` / `nse_expiries`), the RBI MPC schedule (rbi.org.in), the US FOMC schedule (federalreserve.gov), US CPI release dates (bls.gov), the Union Budget date, and results season from `earnings_calendar_events`. No scraping. Admin-editable. | J6-b | open |
| JM-14 | How do manual edits (Z6 tag decisions, merges and splits, renames) interact with re-imports and re-syncs? | (a) Z6 tag decisions are kept as they are: a re-run never overrides CONFIRMED or DISMISSED. (b) A group the trader edited is `user_locked`. A rebuild never regroups its positions, and new fills of those positions extend it. (c) A fill the broker later corrects or removes marks the group "needs review" and notifies the trader; nothing is silently rewritten. (d) Tags and stories follow the group while its identity (its first fill) survives; otherwise they are kept, detached, with a notice. (e) Hand-entered trades are never deleted by an import. A matching imported fill is offered as a "same trade?" merge for the trader to confirm. | J2-c, J2-d, J2-e | open |
| JM-15 | Event calendar: reuse `market_events` or a separate journal table? | Reuse `market_events` with a new action `INFO`. That needs a one-line Risk Guardian change: today every action other than BLOCK falls into the size-cut branch. A test proves that INFO never changes a verdict. One calendar, so Z6's `held_through_event` and the journal agree. | J6-b, `risk_engine/guardian.py` | open |
| JM-16 | Zerodha: reading the user's own trade book and positions through Kite Connect. | `docs/BROKER_DATA_TERMS.md` marks Zerodha execution-only for **market data**. Zerodha intraday candles need its paid historical add-on, so Zerodha accounts get W/D charts from the lake, and 1H/15M only when another of the user's own sessions can serve them. | J2-d, J3-b | open |
| JM-17 | Intraday and option-contract candles for trade charts: source and storage. | The user's own broker historical API through `live_access.user_source` (BT1b), cached **tenant-private** in `md_tenant_candles` with `source = "broker:<name>"`, never in the shared lake. Storing a user's own historical bars for their own use is to confirm per broker in BROKER_DATA_TERMS. | J3-b | open |

Until the bucket exists, the local volume is backed up with the database. | J3-a, J3-b | open |
