# Analyze a chart

Status: **PR-A built** (behind the flag `chart_analyze`, off). PR-B to PR-E are planned below. Owner brief: 2026-10-20
(the feature brief, then the result-screen addition). Open questions: `docs/OPEN_QUESTIONS.md`, section "Analyze a chart
(20 Oct)", CA-1 to CA-7.

The same working rules apply as everywhere in ATP: draft PRs, self-review, tests, PAPER only, LIVE untouched, English
only, tenant-safe, settings-driven, behind a feature flag. This page **places no order and has no order button**; the
result is educational: "what the method sees and the conditions", never a buy / sell call, with the disclaimer on every
result. The method (its instructions, the KB, the reader) is never in this public repository: it lives in the private
package (`docs/design/PRIVATE_PACKAGE.md`), and ATP's public code holds only the boundary (section 7).

## 1. What the user does

1. Opens **Analyze chart** (Markets in the v2 navigation, or the **Analyze a chart** button on the Charts page). Both
   are hidden while the flag is off for the organisation.
2. Adds one chart: **upload** (file picker; paste from the clipboard; drag and drop on a desktop) a PNG / JPEG /
   screenshot, or **paste a link**: a TradingView snapshot link (`tradingview.com/x/...`) or a direct image link.
   A link that cannot be opened (a login wall, a live chart page, an error, a timeout, not an image) says
   **"Please upload a screenshot instead"**. Nothing fails silently.
3. Picks a **mode** - **Image only** or **Hybrid** - and presses **Analyze**. A progress line shows while it runs.
4. Reads the result (section 4), and can **Set an alert on this area**, **Alert me when this happens**, **Download /
   share the result image**, **Delete**, and (hybrid only) **Open in Chart tab**.
5. **History**: the user's own past analyses, newest first; each opens its result again.

Phone first (UI v2 §8 / §9, MOBILE_APP_PLAN §2): one column under 768 px with a 16 px gutter, 44 px targets, no
sideways scroll, nothing behind the bottom bar; on a desktop the original and the annotated image sit side by side.

## 2. The two modes

**A. Image only (PR-A).** The AI reads the picture alone. Every result carries the label **"Image-only analysis: prices
and volume are read from the picture and may be approximate"**; prices are marked approximate everywhere (the
alert form says so too). Annotations are drawn as an overlay on the user's own image, in that image's pixel space.

**B. Hybrid (PR-B, PR-C).** Shown in PR-A, disabled, "Coming soon".

1. **Recognise**: symbol, exchange, timeframe, the visible time range (first and last candle on the axis) and the
   price scale, shown as **editable fields**.
2. **Data**: bars for exactly that symbol / timeframe / range from (a) the user's connected broker (the BrokerGate
   states: connected, login needed, not connected) or (b) ATP's stored market-data lake (the vendor pack: 1-minute data
   resampled to any timeframe). The broker when the user is logged in, otherwise the stored data. With neither: offer
   **Image only** or **Connect your broker**. Never sample data. **Until CA-1 is answered, mode B uses the broker path
   only, and the stored data only for the owner's own tenant** (the HB0 / HB2 rule).
3. **Rebuild** the same chart from real bars (same range, timeframe, candle type) with a volume pane (for NIFTY /
   BANKNIFTY the near-month future's volume, labelled as such) and an RSI pane.
4. **Match check**: compare the rebuilt candles with the uploaded image (the shape of the swings, the highs and lows):
   **"Matches your chart"** or **"Could not match - check symbol / timeframe / range"**. The analysis runs only after
   a match or after the user confirms the fields.
5. **Analyse on the real data**: until the reader is ported, the AI analyses the rebuilt chart together with the
   real-bar facts; as each reader layer is ported (TRADE_TAKEOVER T1-T6), that layer's output replaces the AI part,
   with the same output contract. The reader's areas and lines are drawn on the rebuilt chart (time / price space).

## 3. Storage and retention

- **Where**: the backend's private data volume (`private_data`, mounted at `/data/private` into the backend and the
  worker only; `CHART_ANALYZE_DATA_DIR`, default `/data/private/chart_analyze`). Never under the repository (a root
  inside the source tree is refused), never in git, never served by Caddy or any static route; the image is returned
  only by `GET /api/chart-analyze/items/{id}/image` to its owner, with `Cache-Control: private, no-store`.
- **Layout**: `<tenant id>/<uuid4 hex>.png`, every part generated by the server; each path is checked to resolve
  inside the root. Directories 0700, files 0600, written to a temporary name and renamed.
- **What is stored**: only the cleaned PNG (section 6), never the original bytes. A link stores its host only, never
  the full address. The database row (`chart_analyses`): tenant, user, created_at, mode, source, status, the relative
  file path, the image hash and size, the result JSON, the provider / model / engine version, the cost, whether it
  ran on the user's own key.
- **Running**: an analysis is claimed (`running`, `started_at`) before the AI call; an interrupted request ends it as
  failed (the cleanup is shielded from the cancellation), and a row still running after `running_timeout_minutes`
  (default 10, never below the AI call's own worst case derived from the provider timeout; a crash, a restart) is
  stale - it can be analysed again, deleted and purged, and reserves no cost. A run finishes only its own claim (a
  conditional update on status and `started_at`): a late run never overwrites a re-claimed row or brings back a
  deleted one.
- **Retention**: an admin setting, `retention_days` (default **30**, as the owner proposed). The daily retention job
  (`app.retention.service.run_retention`, run by the trading worker once per IST day outside market hours) deletes
  expired images and results, batch after batch until none is left; a file that could not be removed keeps its path on
the row and is retried (never an orphaned file). **Delete** by the user removes the file and the result at once.
- **Counters**: a deleted or expired row keeps only created_at, mode and cost (status `deleted`) until
  `counter_keep_days` (default 32), so deleting cannot reset a daily or monthly limit; then the row goes too.
- **Account erasure** (`erase_user`) deletes the user's files and rows.
- **Who sees what**: the owning user only (tenant id AND user id on every query). Another member, an organisation
  owner and another organisation get 404. ATP does not offer organisation admins a view of members' personal AI
  records, so this feature does not either.
- **Backups**: the images are short-lived user data and are not in the encrypted files archive (CA-4).

## 4. The output contract and the result screen

Generic names only; the engine (private package) fills them, the public code validates and renders them
(`backend/app/chart_analyze/contract.py`). Image-only coordinates are pixels of the stored image (x right, y down) with
approximate prices; hybrid coordinates are time and price.

| Block | Fields |
|---|---|
| Label, disclaimer | `label` (image-only), `disclaimer` (every result), `approximate_prices`, `coordinate_space` |
| Recognised | `symbol`, `exchange`, `timeframe`, `first_bar`, `last_bar` (as read; editable in hybrid) |
| 1. Annotations | `swings[]` {label HH / HL / LH / LL, point, price}; `areas[]` {side buyer / seller, state fresh / tested / broken / flipped, box, price range, note}; `lines[]` {segment, touches[], note}; `rsi_divergence` {kind, segment on price, segment on the RSI pane}; `commitment_candle`; `ltf_choch`; `setup_lines[]` {trigger / invalidation / next_area, y, price} |
| 2. Story | `story[]` - from the start of the visible range to now, plain words |
| Trend, state, RSI | `trend` {side up / down / sideways / unclear, text}; `current_state` {phase pullback / handover / commitment / trending / range / unclear, text}; `rsi` {divergence bullish / bearish / none, text} |
| 3. Setup | `setup` {side bull_put / bear_call / none, label A / B, status formed / forming / none, waiting_for, trigger, invalidation, next_areas[]} - "what the method sees and the conditions" |
| 4. Evidence | `evidence[]` {name, present, reason} - names from the engine, ✓ / ✗ with one line each; **listed, never scored** |
| 5. Scenarios | `scenarios` {primary, alternative, primary_invalidated_at} - the possibilities on both sides |
| 6. What to wait for | `what_to_wait_for` {condition, alert: above / below / between prices, or none} - only when the setup is not formed |
| 7. Higher timeframes | `htf_context[]` {timeframe, trend, nearest areas} - when the engine returns it |
| 8. Key levels | `key_levels[]` {kind area / line, name, side, state, price range} - a table on desktop, cards on a phone |

Validation, whatever the engine returns: every text goes through the AI output filter (`app.ai.output_filter`); a text
that reads as a call, advice or a guarantee - blocked, or one the filter would only frame as a specific call - is
**withheld** and replaced by a neutral line. Enums, lengths, list sizes
and coordinates are bounded; a point outside the image is dropped. Unknown keys (an `order`, a `score`, a confidence)
are dropped. A missing story, trend, setup or scenario makes the analysis **failed** - nothing partial is shown.

**Buttons.** *Set an alert on this area* and *Alert me when this happens* create an ordinary alert rule through ATP's
existing alert creation (`POST /api/alerts/rules`, an instrument rule with a ScreenQL price condition: `close > p`,
`close < p` or `close >= low and close <= high`), after the user checks the symbol and the prices (marked approximate
in image-only). A condition that is not a price ("a lower-timeframe change of character") says "We can't set an
alert on this condition yet". Alerts need the alert feature (`screener_v2`) as everywhere. *Download / share the
result image* renders the annotated image client-side to a PNG (the user's own image plus the overlay and the label)
and shares it through the Web Share API where available, else downloads it. *Delete* asks first and names the
consequence. No order button anywhere; no "Trade" link.

## 5. The API (PR-A)

| Route | What |
|---|---|
| `GET /api/chart-analyze/status` | engine installed?, modes, the caller's usage against the limits, upload rules, retention, label, disclaimer |
| `POST /api/chart-analyze/items` | multipart: `file` (PNG / JPEG) or `link`, and `mode` → one stored item (201); limits and the rate limit first |
| `GET /api/chart-analyze/items` | the caller's history (no result bodies; a summary per item) |
| `GET /api/chart-analyze/items/{id}` | one item with its result |
| `GET /api/chart-analyze/items/{id}/image` | the cleaned image (410 when retention removed the file) |
| `POST /api/chart-analyze/items/{id}/analyze` | runs Image only (hybrid: 409 "coming soon"); a done item is returned, not re-run |
| `DELETE /api/chart-analyze/items/{id}` | deletes the image and the result |
| `GET / PUT /api/admin/chart-analyze/settings` | SUPER_ADMIN with MFA |

Errors are JSON `{message, code}`: `link_unreadable` (422, message "Please upload a screenshot instead" plus a short
reason), `image_rejected` (413 / 415 / 422), `limit_reached` (429), `not_in_plan` (402), `engine_not_installed` (503),
`no_ai` (409), `hybrid_soon` (409), `storage_unavailable` (503). Flag off: the platform's standard 503 with
`X-Feature-Disabled: chart_analyze`. Every route is in `backend/tests/tenancy_route_table.py`.

## 6. Upload and link-fetch security

**Every image** (upload or fetched) takes one path (`imaging.sanitize`): size limit before parsing; type by magic bytes
only (PNG / JPEG; the name and the declared type are ignored); Pillow limited to the PNG / JPEG decoders; width,
height and pixel count checked from the header before any pixel is decoded (the decompression-bomb limit, and Pillow's
own bomb warning raised as an error); `verify()`, then a fresh open and a full decode; the EXIF orientation applied;
the pixels copied into a new RGB / RGBA image with no metadata and saved as PNG (EXIF, XMP, ICC, text chunks and
trailing bytes gone). Every decode error is a clear 4xx.

**Links** (`linkfetch.py`), on the first request **and every redirect hop**:

- `https` only (plain http is not needed - TradingView and image hosts serve https - and a plain-http image could be
  replaced in transit), port 443, no user name / password, at most 2,048 characters;
- TradingView: only `/x/<id>/` snapshot links are accepted, and the snapshot page is never fetched or parsed: the
  image is read from `s3.tradingview.com/snapshots/<first letter>/<id>.png`; any other TradingView page (a live
  chart, a symbol page) is refused at once as a live page;
- the host is resolved by ATP and **every** address must be public: loopback, private, link-local (cloud metadata),
  multicast, reserved, unspecified, CGNAT 100.64/10, benchmarking, IPv6 unique-local / site-local, NAT64, 6to4 and
  Teredo are refused; an IP literal is checked the same way;
- the connection is **pinned** to the checked address (the request goes to that IP with the real name in `Host` and as
  the TLS SNI / certificate name), so a second DNS answer (rebinding) is never used;
- redirects followed by hand, at most `link_max_redirects` (default 3); no proxy from the environment;
- connect, read and total timeouts (settings); `Accept-Encoding: identity` (a compressed answer is refused, so the size
  limit counts real bytes); the size enforced from Content-Length and while streaming;
- the content type must be image/png or image/jpeg **and** the bytes must start with the PNG / JPEG signature.

- internationalised and full-width host names (`bücher.de`, `ｅxample.com`) are turned into their IDNA / ASCII form
  first (that form is resolved, checked, sent as `Host` and as the TLS name); a raw non-ASCII query is percent-encoded
  as a browser would; a name that cannot be encoded, and any
  other error while fetching, is an unreadable link ("Please upload a screenshot instead"), never a server error.

**Not `EGRESS_ALLOWED_HOSTS`.** That operator allow-list is for destinations an organisation configures once (webhooks,
SMS gateways). Here users paste images from any host, which no list could name; the protection is the public-address
check on every hop plus the pinned connection.

**The decode is CPU-bound** (about a second and some hundred MB for a large image): the API runs it in a worker thread,
at most two at a time per API process (the gate is taken on the event loop before a thread is used, so waiting
decodes hold no worker thread), so the event loop never stalls. 16-bit greyscale is reduced to 8-bit first.

**No lock or connection is held during the slow part**: the plan limit is checked once without a lock, the read
transaction ends, the upload is read / the link fetched / the image decoded, and only the add itself takes a short
per-user transaction advisory lock (`pg_advisory_xact_lock`) to re-check the limit and insert.

Tests use a fake resolver and an `httpx.MockTransport`; nothing reaches the network.

## 7. The boundary to the private package

- `app/chart_analyze/provider.py`: the `AnalysisProvider` interface - `image_only_instructions(width, height)` returns
  the system text, the user text and a prompt version; `parse_image_only(reply, width, height)` turns the model's
  answer into the output contract (section 4). PR-C adds the hybrid entry point with the same contract. The provider
  also names its `version` and `method_version` (the method pack's hash), stored with every analysis.
- `load()` imports `atp_private.chart_analyze.get_provider()`. Not installed (public CI, any host without it): the page
  says **"Analysis engine not installed"**, the analyze route answers 503 `engine_not_installed`, and nothing else
  changes. The loader logs the engine's name and versions only.
- Public tests use a synthetic fake provider with a placeholder instead of instructions; a test checks the public
  package carries no instruction text.

## 8. The AI call

ATP's existing AI path, no new way of holding keys (`app/chart_analyze/engine.py`):

1. **The user's own key (BYOK)** where ATP already allows it (flag `vision_byok`, the user's Vision switch, a key):
   the user's BYOK daily / monthly caps (hard stop), logged in `llm_calls` as billed to the user's key.
2. Else **the organisation's AI provider** (`provider_for`: a plan with AI features, the data-sharing consent, the
   plan's monthly AI budget), metered like every AI call; the image goes through `MeteredProvider` (a pass-through
   added for this feature). This feature's own monthly **cost cap** per plan tier is checked before the call: every
   running analysis reserves one estimate, and spend counts in the month the analysis ran (`analysed_at`).
3. Neither: `no_ai` with what to do ("add your own key in Settings").

The AI never places orders; the feature has no import of the execution, paper, broker or approval code (a test checks).

## 9. Limits and settings

Admin settings (`GET / PUT /api/admin/chart-analyze/settings`, stored as the platform control
`chart_analyze_settings`; defaults in `app/chart_analyze/settings.py` only; bounds refuse a typo):

| Setting | Default |
|---|---|
| `retention_days` / `counter_keep_days` | 30 / 32 |
| `max_image_bytes` | 5 MB (at most the API body limit, 8 MB) |
| `max_image_width` / `max_image_height` / `max_image_pixels` | 4096 / 4096 / 9 million (a 4K screenshot is 8.3 million) |
| `running_timeout_minutes` | 10 |
| `link_connect_timeout_seconds` / `link_read_timeout_seconds` / `link_total_timeout_seconds` | 5 / 10 / 20 |
| `link_max_redirects` | 3 |
| `rate_limit_per_minute` (per user: add + analyze) | 6 |
| `max_output_tokens`, `estimate_input_tokens`, `estimate_output_tokens` | 3000, 3000, 2500 |
| `limits.free` (daily / monthly / cost cap USD a month) | 0 / 0 / 0 - not included |
| `limits.trial` | 2 / 10 / 1 |
| `limits.pro` | 10 / 150 / 10 |
| `limits.business` | 50 / 1000 / 60 |

The tier is `trial` while the subscription is TRIALING, else the plan id. Each chart added (upload or link) is one
analysis. 0 = not in the plan (402); used up = 429 with when it resets (00:00 UTC / the 1st, as the BYOK caps).
Counting is serialised per user. The defaults are provisional (CA-7).

## 10. Flag and beta gating

`chart_analyze` is registered in `FEATURE_FLAGS` and off by default (computed). The owner turns it on for **beta
tenants only** through the flag's tenant allow-list (Admin > Controls > Flags), never globally, until CA-2 (the SEBI
research-analyst position, compliance pack BT7) is answered. Off: every route answers the standard feature-off 503,
and the page, its navigation entry and the Charts-page button are hidden. PR-E's strikes block has its own flag,
`chart_analyze_strikes`, owner's tenant first.
